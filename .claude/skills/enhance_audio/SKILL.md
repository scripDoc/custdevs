# enhance_audio

## Перед выполнением

Прочитай `failures.md` (grep по тегам этого скилла) — если есть релевантные записи, учти их в плане. Не объясняй пользователю что делаешь grep — это фоновая проверка.

**Теги для этого скилла:** #enhance #audio #ffmpeg #denoise #loudnorm #afftdn #acompressor #fallback

## Идеология

На грязных записях (диктофон в офисе, улица, эхо, голоса разной громкости) Whisper срывается: вместо нормальной транскрипции получается каша или большие куски `[BLANK_AUDIO]`. Базовая чистка через ffmpeg-фильтры поднимает точность с ~70% до ~90% на таких записях. На чистых записях (Телемост, Zoom) — обработка не нужна, она наоборот может ухудшить.

Поэтому скилл сам **не решает**, обрабатывать или нет — режим выбирает пользователь в опроснике kickoff (Блок B):
- **a) Хорошее** — пропустить полностью, отдать оригинал в transcribe
- **b) Среднее** — лёгкий enhance (highpass + loudnorm)
- **c) Грязное** — агрессивный enhance (highpass + lowpass + afftdn + loudnorm + acompressor)

## Триггеры

- автоматически из `kickoff` после шага `trim_video` и до шага `transcribe` (по параметру `quality` из опросника)
- «улучши аудио для <клиент>» / «прогони enhance_audio для <клиент>»
- «обработай шумы для <клиент>», «почисти запись <клиент>»

При ручном вызове — спросить одной фразой режим (b или c), если не указан в фразе.

## Параметры из контекста

| Параметр | Источник | Пример |
|---|---|---|
| `client_slug` | имя из фразы / текущий клиент сессии | `aleksandr` |
| `quality` | ответ на вопрос 6 опросника kickoff | `b` или `c` |
| `input` | свежий файл из `clients/<slug>/01_audio/` (без суффикса `_enhanced`) | `clients/aleksandr/01_audio/aleksandr.m4a` |
| `output` | `clients/<slug>/01_audio/<slug>_enhanced.m4a` | — |

## Что делает

1. Если `quality == 'a'` — ничего не делает, отмечает шаг ⏭, выходит.
2. Находит свежий аудио-файл в `clients/<slug>/01_audio/` без суффикса `_enhanced` (это вход — результат `trim_video`).
3. Проверяет, что файл `<slug>_enhanced.m4a` ещё нет (если есть — спрашивает, перезаписать или пропустить).
4. По параметру `quality` выбирает команду:
   - `b` → лёгкий enhance
   - `c` → агрессивный enhance
5. Запускает ffmpeg в фоне с парсингом stderr (см. «Живой прогресс»).
6. После завершения — самопроверка длительности (см. «Самопроверка»).
7. Отчитывается: режим, входной/выходной файлы, длительность работы.

## Команды

### Лёгкий enhance (режим b — среднее качество)

```bash
ffmpeg -y -i <input> \
    -af "highpass=f=80, loudnorm=I=-16:TP=-1.5:LRA=11" \
    -c:a aac -b:a 128k \
    <client_dir>/01_audio/<slug>_enhanced.m4a
```

Что делает:
- `highpass=f=80` — убирает рокот ниже 80 Hz (гул вентилятора, шаги, дыхание в микрофон).
- `loudnorm=I=-16:TP=-1.5:LRA=11` — нормализация громкости до стандарта -16 LUFS, тихие куски подтягиваются ближе к среднему.

### Агрессивный enhance (режим c — грязное качество, два голоса разной громкости)

Типичный сценарий: офис/диктофон, один человек ближе к микрофону, второй дальше.

```bash
ffmpeg -y -i <input> \
    -af "highpass=f=100, lowpass=f=8000, afftdn=nf=-25, dynaudnorm=p=0.95:s=20, acompressor=threshold=-15dB:ratio=2:attack=20:release=200" \
    -c:a aac -b:a 128k \
    <client_dir>/01_audio/<slug>_enhanced.m4a
```

Что делает:
- `highpass=f=100` — отрезает низкие шумы (кондиционер, гул улицы).
- `lowpass=f=8000` — отрезает высокочастотный звон/шипение (выше 8 kHz для речи не нужно).
- `afftdn=nf=-25` — спектральный шумодав, давит ровный фон (постоянный гул, кондиционер).
- `dynaudnorm=p=0.95:s=20` — **динамическая нормализация громкости**: выравнивает уровни локально по окнам ~500 мс (`s=20` кадров), подтягивая тихие фрагменты к пиковой громкости 95% от максимума. В отличие от `loudnorm` (которая поднимает всю запись на одинаковую величину и сохраняет разрыв громкое/тихое), `dynaudnorm` подтягивает каждый кусок независимо — критично, когда один голос близко к мику, второй дальше.
- `acompressor=threshold=-15dB:ratio=2:attack=20:release=200` — мягкая компрессия динамики. Параметры смягчены (threshold -15 vs прежние -18, ratio 2 vs 3), потому что `dynaudnorm` уже выровнял уровни — агрессивная компрессия больше не нужна.

**Не использовать `loudnorm` в этом режиме** — она оставит тихий голос тихим, Whisper его недоразберёт. См. запись в `failures.md` (теги `#dynaudnorm #knowledge`).

## Куда сохраняет

`clients/<slug>/01_audio/<slug>_enhanced.m4a` — рядом с оригиналом, **не перезаписывает** его. Оригинал остаётся для возможных повторных прогонов с другими настройками.

В дальнейших шагах pipeline (`transcribe` и т. д.) автоматически выбирает enhanced-версию, если она есть. Если нет — использует оригинал. Логика выбора — в `transcribe/SKILL.md`.

## Живой прогресс ffmpeg

Лёгкий enhance занимает ~1–2 минуты на час аудио, агрессивный — ~2–4 минуты. На длинных записях (часовых) пользователю нужен живой прогресс, иначе непонятно — процесс идёт или завис.

**Логика:**

1. Запустить ffmpeg в `run_in_background: true`.
2. Каждые **15–30 секунд** опрашивать `BashOutput`/`TaskOutput` по shell_id.
3. В stderr ffmpeg печатает строки вида:
   ```
   size=10240kB time=00:25:30.12 bitrate=178.4kbits/s speed=28x
   ```
4. Парсить из последней такой строки `time=HH:MM:SS.ss`.
5. Считать процент относительно полной длительности входа (через `ffprobe` на старте).
6. Перезаписывать строку статуса (не добавлять новую каждый тик).

**Формат вывода (live):**

```
⏳ Улучшение аудио (агрессивный режим)
        └─ ffmpeg: 47% (35:12 из 74:22, speed 32x)
```

Лейбл режима в первой строке: `(лёгкий режим)` для `b`, `(агрессивный режим)` для `c`.

**Формат вывода (финал):**

```
✅ Улучшение аудио (агрессивный режим)    clients/<slug>/01_audio/<slug>_enhanced.m4a (74:22, 67 МБ, 2:48)
```

**Регламент частоты обновлений:**

- Не чаще раза в 15–20 с — спам токенами.
- Не реже раза в 60 с — пользователь думает, что висит.
- Финальное обновление обязательно — с режимом, длительностью работы, размером выхода.

## Самопроверка после завершения

После успешного выхода ffmpeg — обязательно проверить:

```bash
# Файл создан и не пустой
test -s "clients/<slug>/01_audio/<slug>_enhanced.m4a"

# Длительность совпадает с оригиналом (±1 сек)
DUR_ORIG=$(ffprobe -v error -show_entries format=duration -of csv=p=0 "<input>")
DUR_NEW=$(ffprobe -v error -show_entries format=duration -of csv=p=0 "clients/<slug>/01_audio/<slug>_enhanced.m4a")
# сравнить: abs(DUR_ORIG - DUR_NEW) < 1
```

Если длительности не совпадают (>1 сек разницы) — алярм:
- Удалить кривой `_enhanced.m4a`.
- Записать в `failures.md` с тегами `#enhance #audio #fallback`.
- Сообщить пользователю: «enhance_audio дал кривой файл, fallback на оригинал — transcribe запустится на нём».
- Продолжить pipeline на оригинале.

## Обработка ошибок

- **Файл `<slug>_enhanced.m4a` уже существует** — спросить пользователя одной фразой: перезаписать, использовать существующий, или пропустить enhance.
- **ffmpeg вернул код ≠ 0** — показать последние 10 строк stderr. Не пытаться чинить наугад, не подбирать другие фильтры. Записать в failures.md, сделать fallback на оригинал, продолжить pipeline.
- **Файл создан, но длительности не совпадают** — см. «Самопроверка».
- **Двух неудач хватит** — если enhance упал дважды (например, странный кодек на входе), не пытаться третий раз. Fallback на оригинал, transcribe возьмёт его.

## После выполнения

Оценить результат по трём критериям:

1. **Провал/исправление** — ffmpeg упал, fallback сработал → запись в `failures.md`.
2. **Деградация** — длительность не совпала / выход подозрительно маленький → запись с тегом `#quality`.
3. **Неочевидное знание** — обнаружилась особенность входного формата (например, какой-то кодек ломает определённый фильтр) → запись с тегом `#environment`.

Если ничего из трёх — ничего не пиши.

В отчёте пользователю упоминай факт записи кратко: «Записал в failures.md (теги: #X #Y)».
