# kickoff

## Перед выполнением

Прочитай `failures.md` (grep по тегам всех вложенных скиллов) — если есть релевантные записи, упомяни их кратко в плане. Не объясняй пользователю что делаешь grep — это фоновая проверка.

**Теги для grep:** #kickoff, #pipeline, #orchestrator, #new_client, #ffmpeg, #trim, #webm, #vp8, #transcribe, #deepgram, #diarization, #network, #env, #enhance, #audio, #denoise, #afftdn, #loudnorm

## Идеология

Pipeline кастдева — 5 шагов от добавления клиента до готового транскрипта. Без kickoff пользователь должен помнить порядок и звать каждый скилл руками. С kickoff — один опросник в начале, потом конвейер сам.

**Transcript-only.** kickoff кончается на транскрипте (`02_transcript/`). Старый PDF-разбор (meta → структура → упаковка → PDF) выведен из эксплуатации и лежит в `_archive/old_pdf_pipeline/`. Новый процесс строится **только из транскрипта**: транскрипт уходит в лендинг-офис через Директора (`«сделай лендинг для <клиент>»` / `«запусти офис»`). Стратег офиса читает транскрипт напрямую — никаких промежуточных meta/structure ему не нужно (они искажают картину).

**Принцип «всё на старте».** Все ручные данные собираются **до запуска конвейера**, в опроснике из двух блоков. После старта — автоматика, без пауз и ожидания пользователя. Конвейер пригоден для запуска «уйти за чаем» / «оставить на ночь».

**Аварийный выход:** если что-то пошло не так на любом шаге — стоп, не продолжать. Пользователь чинит и зовёт следующий шаг через его собственный триггер (`new_client`, `trim_video`, `enhance_audio`, `transcribe`). Логика старых триггеров не трогается — kickoff их использует, не подменяет.

## Опросник

Задавай вопросы по одному, дожидаясь ответа на каждый. Не спрашивай списком сразу всё — это нарушает фокус. Если пользователь в первой фразе уже что-то указал (имя, путь к файлу) — пропусти соответствующий вопрос и подтверди понятое.

Опросник делится на два блока:

- **Блок A** — обязательные технические параметры (вопросы 1–4)
- **Блок B** — качество исходной записи (вопрос 5)

### Блок A — технические параметры

1. **Имя клиента?** — «Володя, Анна, Александр и т. д.»
2. **Чем занимается?** — «Одной фразой — пойдёт в шапку meta.md (служебный слот, не используется в офисе, но new_client его заполняет)».
3. **Где лежит исходник записи?**

   **Перед тем как задавать вопрос — просканировать `inbox/`:**

   ```bash
   ls -1 inbox/*.{m4a,mp3,wav,webm,mp4,mov,m4b,opus,aac,flac,ogg,mkv} 2>/dev/null
   ```

   Три исхода:

   - **Один файл** — Q3 не задавать. Сообщить: «Нашёл в `inbox/` файл `<имя>` (длительность `<HH:MM:SS>`) — беру его. Если не он — скажи.» Перед автовыбором — безопасные проверки (см. ниже).
   - **Несколько файлов** — спросить: «В `inbox/` несколько аудио/видео: `1) <A>`, `2) <B>`, `3) <C>`. Какой использовать? (номер, имя или путь снаружи)». Принять номер или имя.
   - **Нет файлов** — задать вопрос явно: «Где лежит исходник? Полный путь, например `~/Загрузки/file.webm`. Или скажи "там" — если уже в `clients/<slug>/00_raw/`.»

   **Безопасные проверки перед автовыбором** (через `ffprobe`):

   - Длительность `< 5 мин` — спросить: «файл короткий (`M:SS`), точно он?»
   - Длительность `> 4 часов` — спросить: «файл длинный (`HH:MM:SS`), возможно нужна обрезка — какие таймкоды?»
   - Расширение видео (`.mp4`, `.mov`, `.mkv`, `.webm`) — подтвердить: «это видеофайл, извлекать аудио?» (дефолт-да через `trim_video` в audio-режиме)
   - Расширение редкое для речи (`.aax`, `.opus`, `.flac`) — спросить: «формат необычный для речи, обрабатывать?»

   Если в чём-то сомневаешься — спрашивай, не угадывай.
4. **Нужно обрезать запись?**
   - Если **да** → «С какого таймкода начало? (например `00:39:11`)» → дождаться → «До какого таймкода конец? (например `01:53:33`)»
   - Если **нет** → пропустить вопросы про таймкоды.

> Вопроса про GPU больше нет: транскрибация идёт через Deepgram (облако), локальные ресурсы не трогаются.

### Блок B — качество исходной записи

5. **Какое качество исходной записи?**
   - **a) Хорошее** — Телемост, Zoom, чистая комната, один-два микрофона близко.
   - **b) Среднее** — диктофон/телефон, тихая обстановка, голоса хорошо слышны.
   - **c) Грязное** — офис с фоновыми звуками, улица, посторонние шумы, эхо, голоса разной громкости.

Этот ответ управляет шагом 4 конвейера (`enhance_audio`):
- `a` → шаг пропускается, transcribe идёт на оригинале.
- `b` → лёгкий enhance (`highpass=80 + loudnorm`).
- `c` → агрессивный enhance (`highpass + lowpass + afftdn + loudnorm + acompressor`).

Подробности — в `.claude/skills/enhance_audio/SKILL.md`.

> **Субъективных наблюдений автора в опроснике больше нет.** Раньше Блок C собирал их в `meta.md` для PDF-разбора. С переходом на transcript-only офис работает только из транскрипта (производные/интерпретации искажают картину — см. `client-strategist`), поэтому Блок C убран вместе с meta-слоем. Если у автора есть важный контекст — он передаётся Директору голосом при запуске офиса, не через файл.

```

```

## Конвейер

После одобрения — гонит шаги по очереди и обновляет статус-таблицу в каждом своём ответе пользователю:

```
[1/5] Создание клиента                         ⏳
[2/5] Архивирование исходника                  ⏸
[3/5] Обрезка записи                           ⏸
[4/5] Улучшение аудио                          ⏸
[5/5] Транскрибация                            ⏸
```

Состояния: ⏳ in-progress, ✅ done, ⚠️ done with warning, ⛔ failed, ⏸ pending, ⏭ skipped.

**Шаг 1 — Создание клиента.** Использует логику скилла `new_client`: транслит slug, `./scripts/new_client.sh <slug>`, заполнение шапки meta.md (имя, дата, деятельность). `meta.md` — служебный слот скелета (new_client его создаёт, в офисе он не используется — не ломаем скелет). Запоминает `<slug>` как «текущий клиент сессии».

**Шаг 2 — Архивирование исходника.** Логика зависит от того, откуда пришёл исходник:

- **Уже в `clients/<slug>/00_raw/`** — отметить ⏭, ничего не делать.
- **В `inbox/`** — **копировать** в `00_raw/`, **сразу после успеха копирования удалить** из inbox (`cp <src> <dst> && rm <src>`). При конфликте имени в 00_raw — добавить суффикс `_2`, `_3` и т. д. Если копирование упало (нет места, нет прав, диск заполнен) — **НЕ удалять** оригинал из inbox, остановить шаг с ошибкой. Сообщить пользователю: «Скопировал `<file>` в `clients/<slug>/00_raw/`, убрал из inbox. Оригинал теперь в `00_raw/` — это основная копия для проекта. Бэкап у тебя на устройствах.»
- **Из любого другого внешнего места** (`~/Загрузки/`, `~/Видео/` и т. п.) — **переместить** (`mv`) в 00_raw, сохранив старое поведение. С защитой от затирания через суффиксы `_2`, `_3`.

**Принцип для inbox:** транзитный буфер. Что лежит — то ещё не запустили. После запуска уходит в папку клиента. Никогда не трогать другие файлы в inbox — только тот, который сам взял для текущего pipeline.

**Шаг 3 — Обрезка записи.** Если опрос сказал «не нужна» — ⏭. Иначе использует логику `trim_video` в audio-режиме (дефолт): `ffmpeg -ss -to -vn -c:a aac -b:a 192k → clients/<slug>/01_audio/<slug>.m4a`. Имя выхода — короткое латинское по slug (`<slug>.m4a` или `<slug>_<MMDD>.m4a` если уже есть).

**Шаг 4 — Улучшение аудио.** Использует логику скилла `enhance_audio`. По параметру `quality` из опросника (Блок B):
- `a` (хорошее) → шаг пропускается, отметить ⏭.
- `b` (среднее) → режим `light`, выход `<slug>_enhanced.m4a`.
- `c` (грязное) → режим `aggressive`, выход `<slug>_enhanced.m4a`.

Если шаг провалился — записать в failures.md (теги `#enhance #audio #fallback`), отметить ⚠️, продолжить pipeline на оригинальном файле (transcribe сам выберет оригинал, если enhanced нет).

**Шаг 5 — Транскрибация (финальный шаг).** Использует логику `transcribe` (см. её SKILL.md) — Deepgram Nova-3 + диаризация v2 (облако), разделение спикеров из коробки. Скилл сам выбирает enhanced-версию из `01_audio/`, если она есть; иначе — оригинал. Ключ `DEEPGRAM_API_KEY` читается из `custdevs/.env`. Результат — `clients/<slug>/02_transcript/<slug>.transcript.{md,txt,json}`. **На этом kickoff завершён.**

> Шаги 3, 4, 5 — длинные. Прогресс отображается автоматически (логика встроена в сами скиллы `trim_video`, `enhance_audio`, `transcribe`).

## Параметры из контекста

| Параметр | Источник | Пример |
|---|---|---|
| `name` | ответ на вопрос 1 (или из триггерной фразы) | «Володя» |
| `slug` | транслит + snake_case | `volodya` |
| `description` | ответ на вопрос 2 | «видеомонтаж для блогеров» |
| `source_path` | ответ на вопрос 3 | `~/Загрузки/Встреча в Телемосте...webm` |
| `start` / `end` | ответы на вопрос 4a/4b | `00:39:11` / `01:53:33` |
| `quality` | ответ на вопрос 5 | `b` (или `a` / `c`) |

## Поведение при ошибках

- **Шаг упал** → отметить ⛔, остановить конвейер, показать stderr/детали.
- **Шаг 4 (`enhance_audio`) упал** → особый случай: отметить ⚠️, записать в failures.md, **продолжить** pipeline на оригинале (это fallback, не остановка). transcribe возьмёт оригинал автоматически.
- **Не пытаться чинить автоматически** на других шагах. Пользователь решает: фиксит проблему и продолжает (через триггер этого шага: `обрежь видео ...`, `улучши аудио ...`, `транскрибируй ...`), или сворачивает.
- **State не теряется.** Папка клиента, исходник в `00_raw/`, m4a в `01_audio/` (оригинал и/или `_enhanced`) и т. д. — всё уже на диске. Старые скиллы работают с теми же путями, продолжение возможно.
- **Двух неудач хватит.** Если один и тот же шаг упал дважды — стоп, не пытаться третий раз тем же способом.

## Состояние сессии

После kickoff в контексте сессии живёт `current_client_slug = <slug>`. Все следующие команды без явного имени относятся к нему:

- «перепрогони транскрипцию» / «давай большую модель» → `transcribe` для текущего клиента
- «улучши аудио агрессивно» → `enhance_audio` с режимом `c` для текущего клиента (если автоматический прогон шёл на `b` и не дал нужного качества)
- «сделай лендинг» / «запусти офис» → передать транскрипт текущего клиента Директору

Контекст сбрасывается, когда пользователь явно зовёт нового клиента (через kickoff или `new_client`).

## Команды

Сами bash-команды описаны в SKILL.md вложенных скиллов. kickoff — оркестратор, не дубль логики. Минимум, что он делает напрямую:

```bash
# Перед стартом конвейера
grep -A 5 "#new_client\|#ffmpeg\|#trim\|#webm\|#transcribe\|#deepgram\|#network\|#env\|#enhance\|#audio" failures.md

# Шаг 1
./scripts/new_client.sh <slug>

# Шаг 2 — архивирование исходника
# Если из inbox/ — копировать и сразу удалить из inbox после успеха копирования
cp "inbox/<filename>" "clients/<slug>/00_raw/<filename>" && rm "inbox/<filename>"
# (если cp упал — rm не выполнится, файл в inbox остался для повтора)

# Если из ~/Загрузки/ или другого внешнего места — переместить (старое поведение)
mv "<source>" "clients/<slug>/00_raw/<filename>"

# Шаг 3 (если обрезать)
ffmpeg -y -ss <start> -to <end> -i "clients/<slug>/00_raw/<source>" \
    -vn -c:a aac -b:a 192k "clients/<slug>/01_audio/<slug>.m4a"

# Шаг 4 (если quality в b/c) — light
ffmpeg -y -i "clients/<slug>/01_audio/<slug>.m4a" \
    -af "highpass=f=80, loudnorm=I=-16:TP=-1.5:LRA=11" \
    -c:a aac -b:a 128k \
    "clients/<slug>/01_audio/<slug>_enhanced.m4a"

# Шаг 4 — aggressive
ffmpeg -y -i "clients/<slug>/01_audio/<slug>.m4a" \
    -af "highpass=f=100, lowpass=f=8000, afftdn=nf=-25, loudnorm=I=-16:TP=-1.5:LRA=11, acompressor=threshold=-18dB:ratio=3:attack=20:release=200" \
    -c:a aac -b:a 128k \
    "clients/<slug>/01_audio/<slug>_enhanced.m4a"

# Шаг 5 — transcribe сам выберет _enhanced.m4a если есть, иначе оригинал.
# Deepgram читает ключ из custdevs/.env; диаризация v2 включена по умолчанию.
python3 -u scripts/transcribe.py "clients/<slug>/01_audio/<input>" \
    -o "clients/<slug>/02_transcript/"
```

## После выполнения

Оценить результат конвейера по трём критериям:

1. **Провал/исправление** — какой-то шаг ломался → запись в `failures.md`.
2. **Деградация** — конвейер прошёл, но с заметным отклонением (медленная транскрипция, кривые границы обрезки, мусорная транскрипция, fallback enhance_audio на оригинал) → запись с тегом `#performance` или `#quality`.
3. **Неочевидное знание** — обнаружилась особенность окружения → запись с тегом `#environment`.

Если ничего из трёх — ничего не пиши.

В отчёте пользователю упоминай факт записи кратко: «Записал в failures.md (теги: #X #Y)».
