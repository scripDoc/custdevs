# kickoff

## Перед выполнением

Прочитай `failures.md` (grep по тегам всех вложенных скиллов) — если есть релевантные записи, упомяни их кратко в плане. Не объясняй пользователю что делаешь grep — это фоновая проверка.

**Теги для grep:** #kickoff, #pipeline, #orchestrator, #new_client, #ffmpeg, #trim, #webm, #vp8, #transcribe, #deepgram, #diarization, #network, #env, #enhance, #audio, #denoise, #afftdn, #loudnorm, #meta, #fill_meta, #package, #pdf, #weasyprint, #layout

## Идеология

Pipeline кастдева — 9 шагов от добавления клиента до финального PDF. Без kickoff пользователь должен помнить порядок и звать каждый скилл руками. С kickoff — один опросник в начале, потом конвейер сам.

**Принцип «всё на старте».** Все ручные данные (включая субъективные наблюдения автора) собираются **до запуска конвейера**, в опроснике из трёх блоков. После старта — автоматика, без пауз и ожидания пользователя. Это убирает разрыв процесса посередине, делает конвейер пригодным для запуска «уйти за чаем» / «оставить на ночь», и снимает риск, что пользователь забудет вернуться к ручному дозаполнению meta и пакет уйдёт без важного контекста.

**Аварийный выход:** если что-то пошло не так на любом шаге — стоп, не продолжать. Пользователь чинит и зовёт следующий шаг через его собственный триггер (`new_client`, `trim_video`, `enhance_audio`, `transcribe`, `fill_meta`, или просто «разбери», «упакуй»). Логика старых триггеров не трогается — kickoff их использует, не подменяет.

- «новый кастдев», «новый клиент», «начнём кастдев»

## Опросник

Задавай вопросы по одному, дожидаясь ответа на каждый. Не спрашивай списком сразу всё — это нарушает фокус. Если пользователь в первой фразе уже что-то указал (имя, путь к файлу) — пропусти соответствующий вопрос и подтверди понятое.

Опросник делится на три блока:

- **Блок A** — обязательные технические параметры (вопросы 1–4)
- **Блок B** — качество исходной записи (вопрос 5)
- **Блок C** — субъективные наблюдения автора, опционально (вопросы 6–13 либо вставка готового блока)

### Блок A — технические параметры

1. **Имя клиента?** — «Володя, Анна, Александр и т. д.»
2. **Чем занимается?** — «Одной фразой — пойдёт в meta.md».
3. **Где лежит исходник записи?**

   **Перед тем как задавать вопрос — просканировать `inbox/`:**

   ```bash
   ls -1 inbox/*.{m4a,mp3,wav,webm,mp4,mov,m4b,opus,aac,flac,ogg,mkv} 2>/dev/null
   ```

   Три исхода:

   - **Один файл** — Q3 не задавать. Сообщить: «Нашёл в `inbox/` файл `<имя>` (длительность `<HH:MM:SS>`) — беру его. Если не он — скажи.» Перед автовыбором — безопасные проверки (см. ниже).
   - **Несколько файлов** — спросить: «В `inbox/` несколько аудио/видео: `1) <A>`, `2) <B>`, `3) <C>`. Какой использовать? (номер, имя или путь снаружи)». Принять номер или имя.
   - **Нет файлов** — задать вопрос явно: «Где лежит исходник? Полный путь, например `~/Загрузки/file.webm`. Или скажи "там" — если уже в `clients/<slug>/00_raw/`.»

   **Безопасные проверки перед автовыбором** (через `ffprobe`):

   - Длительность `< 5 мин` — спросить: «файл короткий (`M:SS`), точно он?»
   - Длительность `> 4 часов` — спросить: «файл длинный (`HH:MM:SS`), возможно нужна обрезка — какие таймкоды?»
   - Расширение видео (`.mp4`, `.mov`, `.mkv`, `.webm`) — подтвердить: «это видеофайл, извлекать аудио?» (дефолт-да через `trim_video` в audio-режиме)
   - Расширение редкое для речи (`.aax`, `.opus`, `.flac`) — спросить: «формат необычный для речи, обрабатывать?»

   Если в чём-то сомневаешься — спрашивай, не угадывай.
4. **Нужно обрезать запись?**
   - Если **да** → «С какого таймкода начало? (например `00:39:11`)» → дождаться → «До какого таймкода конец? (например `01:53:33`)»
   - Если **нет** → пропустить вопросы про таймкоды.

> Вопроса про GPU больше нет: транскрибация идёт через Deepgram (облако), локальные ресурсы не трогаются.

### Блок B — качество исходной записи

5. **Какое качество исходной записи?**
   - **a) Хорошее** — Телемост, Zoom, чистая комната, один-два микрофона близко.
   - **b) Среднее** — диктофон/телефон, тихая обстановка, голоса хорошо слышны.
   - **c) Грязное** — офис с фоновыми звуками, улица, посторонние шумы, эхо, голоса разной громкости.

Этот ответ управляет шагом 4 конвейера (`enhance_audio`):
- `a` → шаг пропускается, transcribe идёт на оригинале.
- `b` → лёгкий enhance (`highpass=80 + loudnorm`).
- `c` → агрессивный enhance (`highpass + lowpass + afftdn + loudnorm + acompressor`).

Подробности — в `.claude/skills/enhance_audio/SKILL.md`.

### Блок C — субъективные наблюдения автора (опционально)

Сначала спроси формат сбора:

> **Хочешь ответить по вопросам или вставить готовый текст наблюдений одним блоком?**
>
> - **Вопросы** — пройдём по 7 коротким вопросам (всё опционально, любой можно пропустить).
> - **Готовый блок** — у тебя уже есть текст с наблюдениями, вставь целиком.
> - **Пропустить** — наблюдений нет / не помню / нет времени.

Дальше — по выбору пользователя:

#### Вариант «Готовый блок»

**Сначала просканировать `inbox/` на наличие .md файлов:**

```bash
ls -1 inbox/*.md 2>/dev/null
```

Три исхода:

- **Один .md файл** — спросить: «Нашёл в `inbox/` файл `<имя>.md` — взять его как блок наблюдений? (Y/N)». Если Y → читать через Read.
- **Несколько .md файлов** — спросить: «В `inbox/` несколько .md: `1) <A>`, `2) <B>`. Какой? (номер/имя/путь снаружи/вставить текст вручную)».
- **Нет .md файлов** — предложить вставку: «В `inbox/` нет .md файлов. Вставить текст блока наблюдений сюда?»

**Логика обработки:**

- Текст вставлен в чат → использовать как есть.
- Файл из `inbox/` → прочитать через Read **и сразу удалить** из inbox после успешной вставки в meta.md (см. шаг 1 конвейера, логика записи раздела наблюдений). При сбое чтения / записи в meta.md — файл в inbox **остаётся**.
- Внешний путь со слэшами → читать через Read, не трогать (внешний файл — не наша зона).

Содержимое без переформатирования попадает в раздел `## Контекстные наблюдения автора (kickoff)` в meta.md — пользователь сам структурирует.

Запомнить выбор: `observation_format = paste`.

#### Вариант «Вопросы»

Задавать **по одному**, не списком. Все вопросы необязательные — на любой можно ответить «—» / «пропустим» / «не помню» / «скип». Не настаивать, не уговаривать.

6. **Откуда знаешь клиента?** (можно пропустить)
   - Тёплый круг (мужской клуб, друзья, рекомендация знакомого).
   - Полу-холодный (рекомендация от знакомого, но лично не знал).
   - Холодный (нашёл сам, никаких связей).

7. **Что заметил в невербалике на встрече?** (можно пропустить)
   - Открытый, легко говорит на любые темы.
   - Зажатый, отвечает коротко, тяжело раскрывается.
   - На разогрев нужно много времени, потом раскрывается.
   - Что-то другое (опиши свободно).

8. **Какой главный паттерн поведения заметил?** (можно пропустить)
   - Быстро принимает решения, действует.
   - Откладывает, нужно толкать к действию.
   - Ясно видит что хочет, но не делает.
   - Делает интенсивно, но без приоритетов.
   - Что-то другое (опиши свободно).

9. **Главные 2–3 боли клиента, которые он сам назвал?** (свободный текст, можно пропустить)
10. **Куда хочет дойти? Какая мета-цель?** (свободный текст, можно пропустить)
11. **Где загорелся огонёк? Где потускнел?** (свободный текст, можно пропустить)
12. **Метафоры и яркие формулировки клиента, которые запомнились?** (свободный текст, можно пропустить)
13. **Твои внутренние реакции — что заметил, что зацепило, какие гипотезы возникли?** (свободный текст, можно пропустить)

Запомнить выбор: `observation_format = questions` + ответы.

#### Вариант «Пропустить»

Раздел `## Контекстные наблюдения автора (kickoff)` в meta.md **не создаётся**. Запомнить выбор: `observation_format = skip`.

### Запись блока C в meta.md

Вставка раздела происходит в шаге 1 конвейера (после `new_client`, до `trim_video`), чтобы все ручные данные были в meta.md ещё до старта обработки.

**Формат для варианта «Вопросы»** — заполняем шаблон ответами, пустые поля и их заголовки пропускаем:

```markdown
## Контекстные наблюдения автора (kickoff)

**Источник знакомства:** <ответ на 6>
**Невербалика:** <ответ на 7>
**Паттерн поведения:** <ответ на 8>

### Главные боли
<ответ на 9 — свободный текст или список>

### Куда хочет дойти
<ответ на 10>

### Где загорелся огонёк / где потускнел
**Огонёк:** <часть из 11, если разделил>
**Потускнел:** <часть из 11, если разделил>

### Метафоры и формулировки
<ответ на 12>

### Внутренние реакции автора
<ответ на 13>
```

Если пользователь не разделил «огонёк/потускнел» в ответе на 11 — просто вставить его текст под общим заголовком «Где загорелся огонёк / где потускнел», без разбиения.

**Формат для варианта «Готовый блок»** — заголовок `## Контекстные наблюдения автора (kickoff)` плюс пользовательский текст ниже как есть, без переформатирования.

**Формат для варианта «Пропустить»** — раздел вообще не создаётся.

Раздел не редактируется и не дополняется скиллом `fill_meta` (см. правило в `templates/meta_prompt.md`). Используется как дополнительный сигнал в `structure_prompt.md` и `package_prompt.md`.

После опроса — собрать план целиком и показать пользователю. **Не запускать**, пока не пришёл «давай» / «поехали» / «ок» / эквивалент.

```
План:

  Клиент:        <Имя> (<деятельность>)  →  clients/<slug>/
  Исходник:      <путь>
  Обрезка:       <start>–<end>  (или: «не нужна»)
  Качество:      хорошее (enhance пропускается)

  Пакет + PDF:   автоматически после разбора (без паузы)
```

## Конвейер

После одобрения — гонит шаги по очереди и обновляет статус-таблицу в каждом своём ответе пользователю:

```
[1/9] Создание клиента + раздел наблюдений     ⏳
[2/9] Архивирование исходника                  ⏸
[3/9] Обрезка записи                           ⏸
[4/9] Улучшение аудио                          ⏸
[5/9] Транскрибация                            ⏸
[6/9] Автозаполнение meta.md                   ⏸
[7/9] Структурный разбор                       ⏸
[8/9] Упаковка пакета                          ⏸
[9/9] Генерация PDF                            ⏸
```

Состояния: ⏳ in-progress, ✅ done, ⚠️ done with warning, ⛔ failed, ⏸ pending, ⏭ skipped.

**Шаг 1 — Создание клиента + раздел наблюдений.** Использует логику скилла `new_client`: транслит slug, `./scripts/new_client.sh <slug>`, заполнение шапки meta.md (имя, дата, деятельность). Запоминает `<slug>` как «текущий клиент сессии». **Сразу же**, в этом же шаге, добавляет в meta.md раздел `## Контекстные наблюдения автора (kickoff)` (если в опроснике выбрано «Вопросы» или «Готовый блок» — см. форматы выше). Если выбрано «Пропустить» — раздел не создаётся.

Если для блока наблюдений был выбран файл из `inbox/<имя>.md`: после успешной вставки содержимого в meta.md — **удалить** этот файл из `inbox/` (`rm inbox/<имя>.md`). Если запись в meta.md упала по любой причине — оригинал в `inbox/` **остаётся** для повторной попытки. Удаление только после успеха.

**Шаг 2 — Архивирование исходника.** Логика зависит от того, откуда пришёл исходник:

- **Уже в `clients/<slug>/00_raw/`** — отметить ⏭, ничего не делать.
- **В `inbox/`** — **копировать** в `00_raw/`, **сразу после успеха копирования удалить** из inbox (`cp <src> <dst> && rm <src>`). При конфликте имени в 00_raw — добавить суффикс `_2`, `_3` и т. д. Если копирование упало (нет места, нет прав, диск заполнен) — **НЕ удалять** оригинал из inbox, остановить шаг с ошибкой. Сообщить пользователю: «Скопировал `<file>` в `clients/<slug>/00_raw/`, убрал из inbox. Оригинал теперь в `00_raw/` — это основная копия для проекта. Бэкап у тебя на устройствах.»
- **Из любого другого внешнего места** (`~/Загрузки/`, `~/Видео/` и т. п.) — **переместить** (`mv`) в 00_raw, сохранив старое поведение. С защитой от затирания через суффиксы `_2`, `_3`.

**Принцип для inbox:** транзитный буфер. Что лежит — то ещё не запустили. После запуска уходит в папку клиента. Никогда не трогать другие файлы в inbox — только тот, который сам взял для текущего pipeline.

**Шаг 3 — Обрезка записи.** Если опрос сказал «не нужна» — ⏭. Иначе использует логику `trim_video` в audio-режиме (дефолт): `ffmpeg -ss -to -vn -c:a aac -b:a 192k → clients/<slug>/01_audio/<slug>.m4a`. Имя выхода — короткое латинское по slug (`<slug>.m4a` или `<slug>_<MMDD>.m4a` если уже есть).

**Шаг 4 — Улучшение аудио.** Использует логику нового скилла `enhance_audio`. По параметру `quality` из опросника (Блок B):
- `a` (хорошее) → шаг пропускается, отметить ⏭.
- `b` (среднее) → режим `light`, выход `<slug>_enhanced.m4a`.
- `c` (грязное) → режим `aggressive`, выход `<slug>_enhanced.m4a`.

Если шаг провалился — записать в failures.md (теги `#enhance #audio #fallback`), отметить ⚠️, продолжить pipeline на оригинальном файле (transcribe сам выберет оригинал, если enhanced нет).

**Шаг 5 — Транскрибация.** Использует логику `transcribe` (см. её SKILL.md) — Deepgram Nova-3 + диаризация v2 (облако), разделение спикеров из коробки. Скилл сам выбирает enhanced-версию из `01_audio/`, если она есть; иначе — оригинал. Ключ `DEEPGRAM_API_KEY` читается из `custdevs/.env`.

> Шаги 3, 4, 5 — длинные. Прогресс отображается автоматически (логика встроена в сами скиллы `trim_video`, `enhance_audio`, `transcribe`).

**Шаг 6 — Автозаполнение meta.md.** Использует логику `fill_meta`: бэкап текущего, подстановка в `templates/meta_prompt.md` содержимого meta + расшифровки, прогон через себя, запись поверх. Раздел `## Контекстные наблюдения автора (kickoff)` (если был добавлен на шаге 1) `fill_meta` не трогает.

**Шаг 7 — Структурный разбор.** Читает `templates/structure_prompt.md` + свежий meta (включая раздел наблюдений из шага 1) + расшифровку, прогоняет через себя, пишет результат в `clients/<slug>/03_structure.md`. В разбор обязательно входят разделы 11–14: метафоры клиента, сегмент, архетип колеса, общий принцип первого шага.

**Шаг 8 — Упаковка пакета.** Запускается **автоматически** сразу после шага 7, без паузы и без ожидания подтверждения пользователя. Читает `templates/package_prompt.md` + свежий `03_structure.md` + meta.md (с разделом наблюдений), прогоняет через себя по строгой структуре (5 секций: Зеркало → Связки → Колесо → Если двигаться → Уточнить + закрытие), пишет результат в `clients/<slug>/04_package.md`. Соблюдает все запреты из промпта (никаких цен, призывов созвониться, диагностики клиента, пошаговых инструкций).

**Шаг 9 — Генерация PDF.** Сразу после шага 8, без дополнительного подтверждения. Использует логику скилла `generate_pdf`: парсинг `04_package.md` по якорным заголовкам, подстановка в `templates/package_template.html`, рендер через WeasyPrint (Python API), постпроверка вёрстки (число страниц, пустые / сиротские страницы), превью первой страницы PNG. Результат — `clients/<slug>/05_final.pdf`.

| `description` | ответ на вопрос 2 | «видеомонтаж для блогеров» |

## Поведение при ошибках

- **Шаг упал** → отметить ⛔, остановить конвейер, показать stderr/детали.
- **Шаг 4 (`enhance_audio`) упал** → особый случай: отметить ⚠️, записать в failures.md, **продолжить** pipeline на оригинале (это fallback, не остановка). transcribe возьмёт оригинал автоматически.
- **Не пытаться чинить автоматически** на других шагах. Пользователь решает: фиксит проблему и продолжает (через триггер этого шага: `обрежь видео ...`, `улучши аудио ...`, `транскрибируй ...`, `заполни мету ...`, `разбери`, `упакуй`), или сворачивает.
- **State не теряется.** Папка клиента, исходник в `00_raw/`, m4a в `01_audio/` (оригинал и/или `_enhanced`) и т. д. — всё уже на диске. Старые скиллы работают с теми же путями, продолжение возможно.
- **Двух неудач хватит.** Если один и тот же шаг упал дважды — стоп, не пытаться третий раз тем же способом.

## Состояние сессии

После kickoff в контексте сессии живёт `current_client_slug = <slug>`. Все следующие команды без явного имени относятся к нему:

- «собери pdf» / «сгенерируй pdf» → шаг 9 для текущего клиента (если `04_package.md` уже есть)
- «упакуй заново» / «перепакуй» → шаги 8 + 9 для текущего клиента
- «перепрогони транскрипцию» / «давай большую модель» → `transcribe` для текущего клиента
- «обнови меты» → `fill_meta` для текущего клиента
- «улучши аудио агрессивно» → `enhance_audio` с режимом `c` для текущего клиента (если автоматический прогон шёл на `b` и не дал нужного качества)

Контекст сбрасывается, когда пользователь явно зовёт нового клиента (через kickoff или `new_client`).

## Команды

Сами bash-команды описаны в SKILL.md вложенных скиллов. kickoff — оркестратор, не дубль логики. Минимум, что он делает напрямую:

```bash
# Перед стартом конвейера
grep -A 5 "#new_client\|#ffmpeg\|#trim\|#webm\|#transcribe\|#deepgram\|#network\|#env\|#enhance\|#audio\|#meta\|#fill_meta" failures.md

# Шаг 1
./scripts/new_client.sh <slug>
# (плюс запись раздела наблюдений в meta.md через Edit/Write — без bash)

# Шаг 2 — архивирование исходника
# Если из inbox/ — копировать и сразу удалить из inbox после успеха копирования
cp "inbox/<filename>" "clients/<slug>/00_raw/<filename>" && rm "inbox/<filename>"
# (если cp упал — rm не выполнится, файл в inbox остался для повтора)

# Если из ~/Загрузки/ или другого внешнего места — переместить (старое поведение)
mv "<source>" "clients/<slug>/00_raw/<filename>"

# Аналогично для observations.md (если был выбран файл из inbox в Блоке C):
# kickoff читает его через Read и вставляет в meta.md. После успешной вставки:
rm "inbox/<observations>.md"

# Шаг 3 (если обрезать)
ffmpeg -y -ss <start> -to <end> -i "clients/<slug>/00_raw/<source>" \
    -vn -c:a aac -b:a 192k "clients/<slug>/01_audio/<slug>.m4a"

# Шаг 4 (если quality в b/c) — light
ffmpeg -y -i "clients/<slug>/01_audio/<slug>.m4a" \
    -af "highpass=f=80, loudnorm=I=-16:TP=-1.5:LRA=11" \
    -c:a aac -b:a 128k \
    "clients/<slug>/01_audio/<slug>_enhanced.m4a"

# Шаг 4 — aggressive
ffmpeg -y -i "clients/<slug>/01_audio/<slug>.m4a" \
    -af "highpass=f=100, lowpass=f=8000, afftdn=nf=-25, loudnorm=I=-16:TP=-1.5:LRA=11, acompressor=threshold=-18dB:ratio=3:attack=20:release=200" \
    -c:a aac -b:a 128k \
    "clients/<slug>/01_audio/<slug>_enhanced.m4a"

# Шаг 5 — transcribe сам выберет _enhanced.m4a если есть, иначе оригинал.
# Deepgram читает ключ из custdevs/.env; диаризация v2 включена по умолчанию.
python3 -u scripts/transcribe.py "clients/<slug>/01_audio/<input>" \
    -o "clients/<slug>/02_transcript/"

# Шаги 6, 7, 8 — без bash, через Read/Write и собственный inference

# Шаг 9 — рендер PDF через WeasyPrint Python API (см. .claude/skills/generate_pdf/SKILL.md)
python3 -c "from weasyprint import HTML; \
HTML(filename='clients/<slug>/_temp_package.html', base_url='clients/<slug>') \
.write_pdf('clients/<slug>/05_final.pdf')"
```

## После выполнения

Оценить результат конвейера по трём критериям:

1. **Провал/исправление** — какой-то шаг ломался → запись в `failures.md`.
2. **Деградация** — конвейер прошёл, но с заметным отклонением (медленная транскрипция, кривые границы обрезки, мусорная транскрипция, fallback enhance_audio на оригинал) → запись с тегом `#performance` или `#quality`.
3. **Неочевидное знание** — обнаружилась особенность окружения → запись с тегом `#environment`.

Если ничего из трёх — ничего не пиши.

В отчёте пользователю упоминай факт записи кратко: «Записал в failures.md (теги: #X #Y)».
