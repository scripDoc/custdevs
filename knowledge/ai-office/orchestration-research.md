# Исследование оркестрирующих систем для AI-Office

Цель: изучить как устроены готовые мульти-агентные системы, чтобы спроектировать своего оркестратора (Директор) и перенять рабочие приёмы.

## 1. zubair-trabzada/ai-marketing-claude

### Структура репозитория

```
market/SKILL.md          ← оркестратор (роутер /market <команда>)
skills/  (14 шт)         ← market-copy, -landing, -funnel, -ads, -emails, -seo, -brand…
agents/  (5 шт)          ← content, conversion, competitive, technical, strategy
scripts/ (4 py)          ← analyze_page, competitor_scanner, social_calendar, generate_pdf
templates/ (6 md)        ← email-секвенции, proposal, content-calendar, checklist
install.sh / uninstall.sh
```

### Как устроена оркестрация

**Оркестратор — это SKILL, не агент.** `market/SKILL.md` = роутер: ловит `/market <команда>` и направляет в нужный sub-skill (`skills/market-<команда>/`). Сам ничего не пишет, только маршрутизирует + задаёт общие стандарты (scoring, output, business-type detection).

**Sequential или parallel — оба, по ситуации:**
- Флагман `/market audit` = **5 агентов параллельно**. Каждый оценивает свою независимую ось (content / conversion / competitive / technical / strategy), считает score, возвращает блок. Зависимостей между ними нет → чистый fan-out.
- Остальные команды = **один skill**, без агентов.
- Между командами — **мягкий sequential через файлы**.

**Передача контекста — через файлы на диске, не через сообщения.** Ключевой приём. У каждой команды фиксированный выход (`MARKETING-AUDIT.md`, `BRAND-VOICE.md`, `COPY-SUGGESTIONS.md`…). Skills связаны блоком «Cross-Skill Integration»:
> «If `BRAND-VOICE.md` exists, use its voice guidelines… If `MARKETING-AUDIT.md` exists, reference the Content & Messaging score…»

То есть skill при запуске проверяет, лежит ли рядом артефакт предыдущего, и подхватывает его. Конвейер не жёсткий — собирается из того, что уже насчитано в текущей папке.

**Human gates — НЕТ.** Система полностью автономна: команда → файл. Ни одной точки подтверждения. Это инструмент аудита, а не диалоговый процесс.

### Что у них есть, чего нет у нас

| Их приём | Что даёт | У нас |
|---|---|---|
| **Оркестратор-роутер** (`/market`) | одна точка входа, диспетчеризация | нет — цепляем агентов вручную |
| **Файловый handoff** («if FILE.md exists») | агенты не зависят от живой передачи, конвейер пересобираем | делаем неявно (`strategist_brief.md`), не формализовано |
| **Scoring-рубрики 0–100** | измеримость, повторяемость, приоритизация | нет числовых рубрик (кроме порога stop-slop 35/50) |
| **Конвенция имён выхода** (UPPERCASE.md) | предсказуемость артефактов | нет конвенции |
| **templates/** | переиспользуемые скелеты (email, proposal) | нет |
| **Python-скрипты** для детерминированных частей | надёжность вне LLM | есть (transcribe, pdf), но не для маркетинга |
| **Parallel fan-out** независимых осей | скорость на аудите | пока sequential |
| **Business-type detection** | ветвление под тип бизнеса | нет |

### Что у нас лучше под нашу задачу

1. **Направление противоположное и это решает всё.** Они **аудируют существующий сайт** (вход = URL через WebFetch). Мы **строим первый лендинг из кастдева** (вход = транскрипт, сайта ещё нет). Их `market-copy` буквально начинается с `WebFetch(url)` — у нас фетчить нечего. Их структура под наш вход не ложится в принципе.
2. **Вход глубже.** У них тонкий scraped-HTML. У нас — первичные качественные данные интервью (боли, язык, возражения из живого разговора). Бриф `client-strategist` богаче любого их аудита.
3. **Дисциплина диаризации** ([Спикер 0] vs [Спикер 1]) — у них нет аналога, они просто «quote examples» со страницы. Наш отлов «это слова интервьюера, не клиента» — то, чего их система не умеет.
4. **VoC-догма (правило №1).** Мы требуем дословные цитаты с таймкодами. Они цитируют свободно — для нас это нарушение.
5. **Русский + правила проекта** (не продавать в разборе и т.д.).

### Что стоит перенять (3 приёма, без смены пути)

1. **Файловый handoff — формализовать.** Прошить в `dr-copywriter`: «контекст бери из `strategist_brief.md`, если он есть рядом». У них это подтверждённый рабочий паттерн, берём как стандарт для всех будущих агентов.
2. **Оркестратор-роутер — наша главная архитектурная развилка.** У них пайплайн собирает не человек, а оркестратор. Для нас это будущий «собери лендинг для <клиент>» (Директор), который сам гонит `client-strategist → dr-copywriter → designer` и кладёт артефакты по конвенции. Заложить в план, но не сейчас — сначала доделать сами агенты.
3. **Измеримый scoring-гейт.** У них каждый выход имеет число. У нас есть готовый порог — `stop-slop` 35/50. Сделать его обязательным gate в `dr-copywriter`, а не «опционально».

**Что НЕ брать:** WebFetch-from-URL flow, 6-осевой marketing-score (заточен под аудит живого сайта), их свободное цитирование, business-type detection (у нас один сегмент — МСБ под AI-автоматизацию).

### Рекомендация

**Наш кастомный путь правильнее — не адаптировать их структуру.** Причина одна и фундаментальная: у них вход = URL существующего сайта и задача = аудит; у нас вход = транскрипт кастдева и задача = построить лендинг с нуля. Это перпендикулярные системы, их каркас под наш вход не натягивается. Но 3 их инженерных приёма (файловый handoff, оркестратор-роутер на потом, обязательный измеримый gate) — переносимы и укрепляют наш путь.

## 2. VoltAgent/awesome-claude-code-subagents

### Структура коллекции

164 субагента в 10 категориях (`categories/01-core-development … 10-research-analysis`) + `install-agents.sh`, README, `.claude-plugin`. Это **библиотека готовых субагентов**, не работающая система — каждый агент самостоятельный `.md`, ставится через installer.

**Ключевое наблюдение: почти все агенты — один жёсткий шаблон на 286 строк.** Структура повторяется независимо от роли:
1. frontmatter (`name`, `description`, `tools`, `model`)
2. вводный абзац «You are a senior …»
3. `When invoked:` — 4 шага активации
4. длинные «прачечные списки» подтем (Content strategy / SEO / Email … по 8 буллетов каждый)
5. `Communication Protocol` — **JSON-запрос к `context-manager`** за контекстом
6. `Development Workflow` — 3 фазы (Planning / Implementation / Excellence)
7. `Progress tracking` — JSON с придуманными метриками
8. `Integration with other agents` — список агентов-соседей для коллаборации
9. финальная строка-девиз

Исключение — `content-quality-editor` (55 строк): конкретный, инструментальный (гоняет `unslop` CLI), без воды. Лучший из прочитанных по плотности.

### Модель межагентного общения

**Централизованный blackboard через `context-manager`.** Каждый агент стартует с JSON-запроса к `context-manager` («дай мне brand voice / design context / market context»), а в конце уведомляет его о результате. То есть общее состояние держит отдельный агент-хранилище, остальные читают/пишут через него.

**Важно:** этот JSON-протокол — **декларативный, не настоящий**. У субагентов Claude Code нет живой шины сообщений; это «косплей» оркестрации в тексте промпта. Реальный handoff у ai-marketing (через файлы) честнее и работает. VoltAgent описывает желаемое, а не исполняемое — там же фейковые метрики («agent selection accuracy > 95%», «avg_response_time 3.2s»).

### Разбор релевантных субагентов по категориям

**Оркестрация (`09-meta-orchestration`) — для нашего Директора:**

| Агент | Что делает | tools | model | Чему учит |
|---|---|---|---|---|
| `agent-organizer` | декомпозиция задачи → подбор команды агентов по capability-matching → дизайн workflow | Read/Write/Edit/Glob/Grep | sonnet | паттерны оркестрации (sequential / parallel / pipeline / map-reduce / hierarchical) перечислены явно |
| `multi-agent-coordinator` | координация конкурентных агентов, синхронизация состояния, обработка отказов | те же | opus | failover/состояние — но абстрактно |
| `workflow-orchestrator` | процессы как state-machine с error handling | те же | opus | моделирование процесса, checkpoints, recovery |
| `context-manager` | хранилище общего состояния, синхронизация доступа | те же | sonnet | идея blackboard (= у нас это файл брифа) |
| `task-distributor` | балансировка нагрузки между агентами | — | — | нам не нужно |

Вывод: оркестраторы VoltAgent — **спека, а не код**. Полезны как словарь паттернов (pipeline, fan-out, hierarchical delegation, checkpoints), но прямого переноса нет — слишком абстрактны и завязаны на несуществующую шину.

**Исследование/стратегия (`10-research-analysis` + `08`) — близко к `client-strategist`:**

| Агент | Что делает | tools | model |
|---|---|---|---|
| `ux-researcher` | юзер-интервью, персоны, инсайты, валидация решений | Read/Grep/Glob/WebFetch/WebSearch (**read-only**) | sonnet |
| `market-researcher` | анализ рынка, поведение потребителя, конкуренты, sizing | read-only | sonnet |
| `research-analyst` | мультиисточниковый research → синтез инсайтов | read-only | sonnet |
| `competitive-analyst` | бенчмарк против конкурентов, позиционирование | read-only | sonnet |
| `search-specialist` | точечный поиск инфы (не синтез) | read-only | sonnet |
| `product-manager` | приоритизация фич, roadmap | Read/Write/Edit/WebFetch/WebSearch | haiku |

Закономерность: **research-агенты read-only** (нет Write) — добывают, не пишут артефакт. Наш `client-strategist` уже так устроен (Read/Glob/Grep/Skill) — VoltAgent подтверждает инстинкт. `ux-researcher` ближе всех к нам по духу (интервью → персона → инсайт), но без диаризации и без VoC-догмы.

**Копи/контент (`08`, `07`) — близко к `dr-copywriter`:**

| Агент | Что делает | tools | model | Перенять |
|---|---|---|---|---|
| `content-marketer` | контент-стратегия, SEO, кампании | Read/Write/Edit/Glob/Grep/WebFetch/WebSearch | haiku | широкий, но размытый — антипример «прачечных списков» |
| `content-quality-editor` | финальная чистка AI-паттернов через `unslop` CLI + редактура | Read/Write/Edit/Bash | haiku | **прямой аналог нашего stop-slop gate** — конкретный, инструментальный, с quality-gate чеклистом |
| `seo-specialist` | тех-аудит SEO, ключи, ранжирование | read-only | haiku | для нас вторично |

`content-quality-editor` — лучшая находка для копи-ветки: показывает, как оформить QA-шаг как **инструмент + чеклист гейта**, а не размытую инструкцию. Ровно то, что мы хотим со stop-slop.

**Дизайн/frontend (`01`) — для `landing-designer` и `frontend-dev`:**

| Агент | Что делает | tools | model | Перенять |
|---|---|---|---|---|
| `ui-designer` | визуальный дизайн, дизайн-системы, компоненты, handoff | Read/Write/Edit/Bash/Glob/Grep | sonnet | чистый цикл **Context → Execution → Handoff**, accessibility (WCAG), design tokens |
| `frontend-developer` | сборка фронта (React/Vue/Angular) | Read/Write/Edit/Bash/Glob/Grep | sonnet | мультифреймворк (нам избыточно — у нас статический HTML-лендинг) |
| `design-bridge` | **переводит `DESIGN.md` (бренд-спеку) в инструкции для сборки UI под нужный бренд** | +WebFetch/WebSearch | **opus** | прямой паттерн для `landing-designer`: «бренд-спека → сборка», и осознанно opus за дизайн-суждение |

`design-bridge` — важная находка: отдельный шаг «спецификация бренда/дизайна → инструкции для верстки». Стыкуется с нашим skill `frontend-design`: бриф → бренд-спека → сборка лендинга.

### Что перенять из VoltAgent

1. **Модель-тиринг по роли.** Они осознанно раздают модели: `haiku` — механическое (content-marketer, seo, product-manager), `sonnet` — исследование/дизайн, `opus` — оркестрация и дизайн-суждение (design-bridge, coordinator). Применить: Директор = opus, специалисты = sonnet, тупой QA = haiku.
2. **`When invoked:` — контракт активации** (4 коротких шага в начале промпта). Чисто и явно. Стоит добавить в наши агенты.
3. **`Integration with other agents` — секция с соседями.** Каждый агент называет upstream/downstream. Делает пайплайн самодокументируемым — ровно то, что Директор будет читать, чтобы строить цепочку. Лёгкая версия оркестрации без шины.
4. **Tool-минимализм по роли.** Research read-only, builders получают Write/Bash. Безопасность + ясность намерения. Наш `client-strategist` уже такой.
5. **QA как инструмент+гейт (`content-quality-editor`).** Оформить stop-slop-шаг как конкретный прогон + чеклист порога, а не размытую просьбу «почисти».
6. **`design-bridge`-паттерн** для `landing-designer`: явный шаг «бренд/дизайн-спека → сборка», модель opus.

### Что НЕ брать

- **Раздутый 286-строчный шаблон** с «прачечными списками» подтем — это наполнитель, не операционная инструкция. Наши агенты плотнее и конкретнее, это преимущество.
- **Фейковый JSON-протокол к context-manager** — у субагентов нет живой шины; это текстовый косплей. Реальный handoff = файлы (ai-marketing прав).
- **Delivery notification с придуманными метриками** («234% traffic», «3.2s») — прямое нарушение нашего правила честности (не выдумывать).

## Выводы для нашего Директора (накапливаются)

Из ai-marketing-claude:
- Файловый handoff между агентами — формализовать (артефакт от предыдущего агента подхватывается следующим)
- Оркестратор-роутер — цель на потом (Директор), не сейчас
- Измеримый gate (stop-slop 35/50) — обязательный, не опциональный
- Конвенция имён выходных файлов — стоит завести

Из VoltAgent:
- **Модель-тиринг по роли:** Директор = opus, специалисты (стратег/копи/дизайн) = sonnet, механический QA = haiku
- **`When invoked:` контракт активации** + **`Integration with other agents`** (явные upstream/downstream) — делают пайплайн самодокументируемым и читаемым для Директора. Это лёгкая оркестрация без фейковой шины
- **context-manager = у нас это файл брифа.** Не плодить отдельного агента-хранилище; blackboard = `strategist_brief.md` и его соседи на диске. Handoff остаётся файловым (честно и работает)
- **Tool-минимализм по роли:** research-агенты read-only, builders получают Write/Bash — безопасность и ясность намерения
- **QA-шаг оформлять как инструмент + чеклист гейта** (паттерн `content-quality-editor`), а не размытую инструкцию
- **`design-bridge`-паттерн** для `landing-designer`: отдельный шаг «бренд-спека → сборка», модель opus
- **Анти-урок:** не скатываться в раздутый VoltAgent-шаблон с прачечными списками и придуманными метриками — держать агенты плотными и честными
