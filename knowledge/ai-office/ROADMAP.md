# AI-Office ROADMAP

Живой план реализации мульти-агентной системы для производства лендингов под клиентов кастдева. Источник истины по архитектуре офиса.

## Архитектура

### Pipeline (sequential, файловый handoff)
транскрипт кастдева (с диаризацией)
→ client-strategist     [что клиент хочет — по реакции, взвешенно]
→ product-architect     [фильтр реализуемости + реальные цифры, 2 выхода]
→ dr-copywriter         [продаёт хотелки в рамках реального]
→ landing-designer      [дизайн из копи]
→ frontend-dev          [код + деплой (сам, через skill deploy_landing)]
Директор — оркеструет всю цепочку, ведёт диагностику. Обязателен для боевой работы.

### Модель автономности

ЦЕЛЬ: полная автономность. Директор сам решает что в его компетенции, к Алику идёт только когда сам не может (редко). На выходе — готовый результат + диагностический отчёт.

**Два РЕЖИМА** (не gates на каждом шаге — это уровень автономности одного и того же Директора, настройка, не переписывание):
- **РЕЖИМ ОТЛАДКИ (сейчас):** детальное логирование каждого прогона. Алик смотрит как каждый агент отрабатывает, может вмешаться. Цель — убедиться что агенты работают корректно.
- **РЕЖИМ ПРОДАКШН (цель):** полностью автономный прогон. На выходе — готовый лендинг + отчёт. Эскалация к Алику только в крайних случаях.

**Этапы развития:**
- **ЭТАП 1:** автономный прогон цепочки + детальные логи + диагностический отчёт. Агенты передают работу друг другу поэтапно (файловый handoff, как живые сотрудники). Директор следит что цепочка идёт корректно.
- **ЭТАП 2:** Директор включается в процесс, когда у агентов есть предложения/вопросы — подзывает нужных агентов, они решают совместно, результат возвращается в pipeline («поднятие руки»).
- **ПОТОМ:** оценить эффективность на практике.

**Эскалация к Алику — техническое ограничение.** Эскалация = Директор ОСТАНАВЛИВАЕТСЯ и возвращает «решил всё кроме X, нужно решение Алика», Алик отвечает, Директор продолжает с этой точки. Это НЕ «живой звонок посреди прогона» (субагенты неинтерактивны). Для редких случаев нормально. В отчёте видно где и почему остановился.

### Принципы
- Каждый агент ДОВЕРЯЕТ предыдущему и углубляет, НЕ перепроверяет с нуля. Не дублировать роли → видно какой этап проседает.
- Источник истины — транскрипт с диаризацией. Производные файлы (старые meta/structure/package по PDF-логике) НЕ давать агентам — искажают. Только стратег читает транскрипт, остальные доверяют артефакту предыдущего.
- Узнавание, не пересказ: клиент должен УЗНАВАТЬ свою картину ("да, вот это я искал"), а не слышать пересказ слов. Не цитировать в лоб.
- Баланс: резонировать с миром клиента + держать планку качества презентации. Не гладкий корпоративный маркетинг, но и не сырые цитаты.
- Взвешивание реакции клиента (стратег): три уровня (высокий/средний/низкий), не бинарно. При сомнении — перечитать транскрипт глубже. Калибровать по личности клиента.
- Честность + эскалация: не знаешь → ищи в интернете (где разрешено) → не решил → Директор → не решил → Алик. Не замалчивать, не придумывать.
- Модели: сейчас **ВСЁ на opus** (качество — приоритет на этапе отладки). Все агенты — стратег, архитектор, копирайтер, дизайнер, frontend-dev, qa-controller, Директор — на opus.
- ОПТИМИЗАЦИЯ (после отладки, если opus много потребляет): кандидаты на понижение до sonnet — **frontend-dev** (собирает HTML по готовой спеке = механика) и **qa-controller** (проверка по чеклисту = механика). Понижать по факту, если качество не падает. Думающие роли (стратег, архитектор, копирайтер, дизайнер) остаются opus.

## Агенты

### client-strategist ✅ собран, отлажен
Вход: транскрипт. Выход: strategist_brief.md.
Анализирует что клиент хочет по реакции (взвешивание), различает спикеров, формирует разделы: аватар / awareness (Schwartz) / оффер / механизм / VoC-цитаты / "Стоп-лист: не использовать" / "Слабые сигналы на будущее".
Tools: Read, Write, Glob, Grep, Skill.

### product-architect — фильтр реализуемости (КРИТИЧНОЕ звено) 🛠 собран (черновик, не тестирован)
Проблема которую решает: pipeline продаёт желания, не проверяя реализуемо ли. Сочинённые цифры ("за 5 минут" — откуда?) недопустимы.
Роль: ДАЁТ копирайтеру что нужно (реальное + цифры + возможности), копирайтер сам решает что использовать. НЕ режет за копирайтера, НЕ грузит техническими деталями. Может ПРЕДЛАГАТЬ (предложения идут обратно стратегу — в Этапе 2 через Директора; в Этапе 1 пишет в заметки, Алик читает).
Оценивает через призму Claude Code + доступных инструментов — НЕ ограничен навыками Алика (с Claude Code возможно многое).
Вход: strategist_brief.md.
ДВА выхода (оба сразу):
  - product_spec_brief.md — для копирайтера. Сжатая рамка реальности: что реально + цифры, что не обещать. Без технических потрохов.
  - product_plan.md — для Алика. Подробный план реализации: что, как, стек, этапы, готовый роадмап который останется запустить в новом проекте для клиента.
Честность: знает → оценка; не уверен → ищет в интернете, проверяет (API, цены, лимиты); не решил → эскалация. Цифры обоснованы или честное "надо измерить/прототип". НЕ сочинять.
Финальная проверка реализуемости — за Аликом.
Tools: Read, Write, Skill, WebSearch, WebFetch (интернет для проверки фактов).
Модель: **opus** (оценка реализуемости + проверка фактов = сложное рассуждение; решено на сборке).

### dr-copywriter ✅ собран (НЕ тестирован)
Вход: strategist_brief.md + product_spec_brief.md (рамка реального от архитектора).
Продаёт хотелки клиента в пределах реального, оформляет продающе (копирайтер = и маркетолог). Оркеструет skills: headline-matrix, objection-crusher, conversion-path-builder, copywriting → чистка generic-language-killer → stop-slop (обязательный gate ≥35/50) → humanizer.
**stop-slop остаётся встроенным в копирайтера** (обязательный gate ≥35/50). qa-controller — дополнительный слой контроля поверх, НЕ замена stop-slop: копирайтер сам чистит свой текст, QA проверяет результат всего pipeline.
Выход: copywriter_draft.md. Доверяет брифу, в транскрипт не лезет.
Tools: Read, Write, Edit, Skill.
Модель: opus.

### landing-designer 🛠 собран (черновик, не тестирован)
Вход: copywriter_draft.md. Паттерн design-bridge + skill frontend-design (первым). Выход: design_spec.md. Anti-convergence (каждый лендинг уникален). Cialdini-триггеры. Модель opus.

### frontend-dev 🛠 собран (черновик, не тестирован)
Вход: design_spec.md + copywriter_draft.md (точные слова). Узко под статический HTML, без мультифреймворк-раздувания. Lighthouse ≥95, accessibility, SEO. Выход: код в deliverables/<slug>/.
**Деплой — САМ** (не Директор): после готового кода вызывает skill `deploy_landing` (автодеплой на Vercel) → live URL. Fallback: если автодеплой заблокируется (классификатор на outward-facing действие) — готовит всё к деплою и сообщает Алику точную команду для ручного запуска. НЕ блокер — либо авто, либо руками, процесс не встаёт.
Модель: opus (кандидат на понижение до sonnet после отладки — сборка HTML по готовой спеке = механика).

### qa-controller — контроль качества ⬜ [собрать после основных]
**ОТДЕЛЬНЫЙ агент** (решено — не скилл Директора). Обоснование: чистое разделение ролей (в отчёте Директора видно отдельную строку QA), изоляция для диагностики (видно, проседает ли контроль качества как этап), гибкость вызова на разных точках.
Роль: проверяет результат (выдуманные факты, AI-slop, несоответствие брифу/реальности). Проверяет на ключевых точках + финал перед выдачей. Сигналит Директору о проблемах → Директор решает: вернуть на доработку или принять.
Кирпичи: stop-slop, content-quality-editor паттерн (из ресёрча). Поверх встроенного в копирайтера stop-slop, не замена.
Модель: opus (сейчас; кандидат на понижение до sonnet после отладки — проверка по чеклисту = механика).

### Директор — оркестратор 🛠 собран (черновик, не тестирован), обязателен для боевой работы
Директор = главный агент-оркестратор. Цель — **автономность**. Запускает весь pipeline по команде "собери лендинг для <клиент>".
- Оркеструет цепочку (файловый handoff, агенты передают работу поэтапно — как живые сотрудники).
- **РЕШАЕТ САМ** что в его компетенции (на то и директор — не дёргает Алика по мелочам).
- **Эскалирует Алику только когда сам не может** (остановка + возврат «решил всё кроме X», редко).
- **ЛОГИРУЕТ каждый прогон детально** (что каждый агент делал — для разбора).
- **ДИАГНОСТИЧЕСКИЙ ОТЧЁТ** (_director_report.md): что делали агенты; были ли общения между ними и что решали; какие решения Директор принял БЕЗ Алика; эскалации (где не смог сам). Алик читает отчёт постфактум, в логи заглядывает если нужно больше деталей.
- Технический паттерн оркестрации — взять из orchestration-research.md (agent-organizer, multi-agent-coordinator, "When invoked / Integration with other agents").
- Модель: opus.

(Раньше тут были «4 human gates на каждом этапе» — УБРАНО, это не модель Алика. Вместо gates — автономность + отчёт + редкая эскалация. См. раздел «Модель автономности».)

Деплой — НЕ обязанность Директора. Директор оркеструет, **деплоит сам frontend-dev** (через skill `deploy_landing`). Директором деплой не грузить.

### Логирование (RUN ID + timestamp, ВСЕГДА)
Логи ведутся **всегда** (не только в режиме отладки) — для оптимизации и трассируемости.
- Каждый прогон получает **RUN ID** (уникальный номер прогона). Директор присваивает его в начале прогона и **прокидывает агентам** (вместе с датой) — они логируют с ним.
- Каждое действие агента логируется с **timestamp (время) + RUN ID**.
- Лог пишется в `clients/<slug>/_run_logs/run_<id>_<date>.log`.
- Зачем: сравнивать прогоны между собой («в прогоне №3 стратег дал X, в №5 — Y»), видеть тренды где регулярно проседает, синхронизироваться по номеру + времени.
- Лог (сырой, по действиям) ≠ `_director_report.md` (свод/диагностика). Отчёт — для чтения Аликом постфактум, лог — для глубокого разбора и сравнения прогонов.

## Голос сотрудника (_agent_notes.md)
Файл ОБЩИЙ на клиента (clients/<slug>/_agent_notes.md), в папке клиента → пометка клиента не нужна.
Формат: "## КТО → КОМУ · дата" + замечание/предложение + важность.
ЭТАП 1: агенты пишут, Алик читает и дописывает решения вручную ("## Решение (Алик)").
ЭТАП 2: Директор читает, маршрутизирует, ведёт решения сам.
Правило: писать только когда реально есть что сказать (не спамить).
