### 2026-05-01 — cuBLAS падает при занятой voice-input даже на medium
**Контекст:** smoke-тест transcribe.py с device=cuda, compute_type float16 и int8_float16
**Симптом:** модель грузится, но на первом сегменте инференса cuBLAS_STATUS_NOT_SUPPORTED. Не OOM — рабочие буферы cuBLAS не выделяются.
**Причина:** voice-input daemon (faster-whisper medium всегда в памяти) забирает достаточно VRAM, чтобы загрузка модели прошла, но при инференсе cuBLAS не может выделить рабочие буферы.
**Решение:** автофоллбэк на CPU при cuBLAS-ошибках добавлен в transcribe.py. Пользователь может явно остановить voice-input через `systemctl --user stop voice-input` для GPU-режима.
**Правило на будущее:** на машинах где постоянно работает другой потребитель CUDA — закладывай не только OOM на load, но и cuBLAS на inference. Грузится ≠ работает.
**Теги:** #cuda #cublas #vram #voice-input #fallback #transcribe

### 2026-05-01 — ffmpeg -c copy webm→mp4 падает на vp8
**Контекст:** trim_video скилл, файл `Встреча в Телемосте *.webm` от Yandex Телемост
**Симптом:** `Could not find tag for codec vp8 in stream #0, codec not currently supported in container`. Conversion failed на запись header'а mp4.
**Причина:** webm от Телемоста = vp8 (видео) + opus (аудио). mp4 контейнер не поддерживает vp8. Команда с `-c copy` пытается запихнуть vp8 в mp4 без перекодирования.
**Решение:** для кастдева видео не нужно — извлекать только аудио в .m4a через `-vn -c:a aac`. Скилл trim_video переработан: дефолт audio-only, видео по явному запросу с правильным выбором стратегии (copy vs re-encode по совместимости кодеков и контейнеров).
**Правило на будущее:** перед `-c copy` проверять совместимость кодеков с целевым контейнером. Для кастдева — всегда audio-only по дефолту.
**Теги:** #ffmpeg #trim #webm #vp8 #codec #container

### 2026-05-01 — Подтверждено: автофоллбэк cuBLAS→CPU работает на боевом часовом аудио 💡 knowledge
**Контекст:** транскрибация `clients/vladimir/01_audio/telemost_30-04-26.m4a` (74 минуты аудио), `medium` на `cuda`, voice-input активен.
**Что наблюдалось:**
1. cuda+float16 → OOM (ожидаемо при активном voice-input).
2. Автофоллбэк на int8_float16 — модель загрузилась.
3. **На первом сегменте инференса cuBLAS упал** (как и на тестовом файле раньше) — встроенный в `transcribe.py` `_is_cublas_error` поймал, скрипт пересоздал модель на `cpu+int8`, перезапустил транскрипцию.
4. Полный прогон на CPU: 74 минуты аудио → 63 минуты wall-clock, скорость x1.2 на 4 ядрах. Файлы корректные, текст осмысленный.
**Бытовое наблюдение:** в реальном времени по `head -10` лога легко увидеть только OOM-fallback на загрузке и не увидеть cuBLAS-fallback на инференсе (он на ~13-й строке, после нескольких строк прогресса). Финальная строка `Устройство: cpu (int8)` — единственный однозначный признак, на чём именно прошло. Не делать выводы о GPU-режиме без неё.
**Baseline для ETA на этой машине (CPU/medium):** 1 час аудио ≈ 50–55 минут wall-clock (x1.1–1.2). Использовать для прикидок до тех пор, пока не появится регулярный GPU-режим с auto-stop voice-input.
**Что НЕ значит эта запись:** это не деградация — на этой машине без auto-stop voice-input GPU-режим невозможен в принципе (cuBLAS падает), и x1.2 на CPU — ожидаемая скорость, не отклонение.

### 2026-05-01 — Не забыть вернуть voice-input после auto-stop ⚠️ knowledge
**Контекст:** `transcribe` в GPU-режиме и `kickoff` останавливают voice-input через `systemctl --user stop voice-input`. Без `trap`/`finally` можно забыть включить обратно при падении транскрипции — daemon останется выключенным до явной команды пользователя, голосовой ввод не работает.
**Симптом:** после неудачного прогона голосовой ввод молча не работает, пользователь не сразу понимает почему.
**Решение:** auto-управление voice-input обёрнуто в bash `trap EXIT` (или try/finally на оркестраторе). Гарантированный старт обратно — даже на исключении в python-скрипте, даже при `Ctrl+C`.
**Правило на будущее:** любое временное выключение системного daemon — только через `trap` или `finally`. Не «выключил → запустил → включил» линейно, потому что между шагами может быть исключение.
**Теги:** #voice-input #systemctl #cleanup #gpu #environment

### 2026-05-02 — Тест-прогон WeasyPrint: сирота-закрытие на доп. странице ⚠️ деградация
**Контекст:** первый боевой прогон `generate_pdf` через WeasyPrint, тестовый клиент `test_volodya` (запись Володи), `04_package.md` ≈ 880 слов чистого текста.

Стр. 6 — плотная (1141 chars: callout «Что важно» + «Если решишь двигаться» + «Что ещё стоит уточнить»), физически закрытие туда не лезет даже с уплотнённым CSS.
**Что попробовали (две правки шаблона):**
1. Убрали `class="section-break"` с трёх h2 (Связки, Режим, Если двигаться) → стр. 8 → 7. Помогло.
2. Добавили `page-break-before: avoid` на `.closing` + уменьшили `margin-top` 36→14 px, шрифт 14→13.5 pt, удалили жирные margin у `<hr>` → 7 → 7. Не помогло, WeasyPrint всё равно вынес закрытие на отдельную страницу.

**Решение (на будущее):** автоматическая пересборка работает до уровня правки CSS, дальше упирается в физику. Дальнейшие варианты:
- Сократить «Что ещё стоит уточнить» с 5 пунктов до 3 (правка в `package_prompt.md` или ручное урезание).
- Повышать пороги детекции сироты в постпроверке (`< 200` → `< 400 chars`) — сейчас 210 chars не ловится, хотя визуально страница пуста.
- Терпеть 7 страниц как норму для пакетов с 5 шестерёнками (норма «4–6» актуальна для меньших разборов; 7 для большого колеса — допустимо).
**Правило на будущее:** перед автоматической корректировкой проверять, **сколько вертикали реально занимает каждый блок**. Если предыдущая страница > 1000 chars — закрытие туда не уберётся никаким CSS-флагом, нужно либо урезать контент, либо принимать +1 страницу.

### 2026-05-02 — wkhtmltopdf удалён из Manjaro, использовать WeasyPrint 💡 knowledge
**Контекст:** установка зависимостей для скилла `generate_pdf` на Manjaro 26.
**Симптом:** `sudo pacman -S wkhtmltopdf` → «не найдена цель: wkhtmltopdf».

Шаблон `templates/package_template.html` совместим без правок (sans-serif fallback в шрифтовом стеке уже был, `@page` и `page-break-*` поддерживаются).
**Правило на будущее:** при установке Python-инструментов для PDF/HTML на Manjaro — проверять статус пакета в репозиториях (`pacman -Si <name>`), не полагаться на старые туториалы.

### 2026-05-03 — dynaudnorm вместо loudnorm для двух голосов разной громкости 💡 knowledge
**Контекст:** агрессивный режим `enhance_audio` (квалификатор `c`) для записей с диктофона / в офисе, где один голос близко к микрофону, второй дальше.
**Симптом:** на старой цепочке `loudnorm=I=-16` тихий голос оставался тихим — `loudnorm` поднимает всю запись на одинаковую величину, сохраняя разрыв громкое/тихое. `acompressor` сжимает только громкие пики, тихий голос не подтягивает. В результате Whisper хорошо разбирал ближнего собеседника и плохо дальнего.
**Причина:** `loudnorm` — глобальная нормализация (по всей записи, целевой LUFS). Для разности уровней между говорящими нужна **локальная** нормализация по окнам.
**Решение:** заменили `loudnorm` на `dynaudnorm=p=0.95:s=20` — динамическая нормализация выравнивает громкость локально, подтягивая каждый кусок (~500 мс окно) к пиковой громкости независимо. Параметры `acompressor` смягчены (`threshold=-15dB:ratio=2` вместо `-18dB:ratio=3`), потому что после `dynaudnorm` агрессивная компрессия не нужна. Лёгкий режим (`b`) не трогали — там тихая обстановка, разница в громкости не критична.
**Правило на будущее:** для двух голосов разной громкости — `dynaudnorm`, не `loudnorm`. `loudnorm` подходит только для записей с одним говорящим или равномерным уровнем.
**Теги:** #audio #enhance #ffmpeg #dynaudnorm #loudnorm #knowledge

3. **Средняя скорость x1.4** на 6170с аудио → 4516с wall-clock (~75 минут).
4. Ожидание для cuda+float16 на medium на этой GPU (GTX 1650 SUPER, 4 ГБ, voice-input выключен) было x5–x10. Получили x1.4 — **в ~5 раз ниже ожидания**.

**Решение:** не блокер — транскрипт получился чистый и осмысленный, конвейер прошёл целиком. Не пересобирали. **Уже отражено в BACKLOG.md** темой «Оптимизация VAD на больших аудио в GPU-режиме» (2026-05-02): варианты — VAD на GPU, отключить VAD в GPU-режиме, или замена на лёгкий silero. Этот кейс — второе подтверждение проблемы (после теста на Володе) на боевой записи 1:42, дополняет статистику для решения.
**Что НЕ значит эта запись:** это не cuBLAS-фоллбэк, не OOM, voice-input корректно выключался и включался обратно через trap. Это деградация именно скорости GPU-инференса на длинных файлах из-за CPU-VAD.
**Правило на будущее:** на этой машине, если ETA важен — для часовых записей реалистично закладывать **~75 минут wall** (x1.4) на medium+cuda+float16 с включённым VAD, а не 12–18 минут как наивная оценка по «GPU быстрее в 5–10 раз». Когда BACKLOG-тема будет реализована — пересмотреть baseline.

### 2026-05-07 — cuBLAS busy-loop после suspend/wake — нет graceful fallback ⚠️ деградация
**Контекст:** транскрибация `sergey_psiholog` (39:19 аудио), `medium` на `cuda+float16`, voice-input остановлен через trap. ПК ушёл в спящий режим в середине прогона, потом проснулся.
**Симптом:** до suspend — нормальный темп x1.3–1.4. После wake — лог `transcribe.py` стух на 25:51/39:19 (66%). Процесс жив, 98% CPU, но GPU utilization упал в 3–4%, `/proc/PID/io` не растёт, worker thread в `R`-state с `wchan=0` (busy-loop без syscalls). `cuda-EvtHandlr` и `cuda00001c00008` потоки — в `do_sys_poll`, ждут события CUDA, которых нет. В результате процесс крутил CPU без прогресса 20+ минут.
**Причина (гипотеза):** suspend ломает CUDA-контекст. После wake `ctranslate2`/`faster-whisper` не получает graceful fallback на CPU — застревает в busy-loop ожидая события от мёртвого CUDA-контекста. Автофоллбэк cuBLAS→CPU из записи 2026-05-01 срабатывает только при первом cuBLAS-вызове, не во время прогона.
**Решение:** `kill -TERM` на процессе, перезапуск на `--device cpu --compute-type int8` (с нуля, faster-whisper не умеет resume). Trap voice-input корректно сработал на SIGTERM.
**Правило на будущее:** перед длинными GPU-транскрипциями блокировать suspend (`systemd-inhibit --who=transcribe --why="long GPU job" --mode=block sleep INF &` параллельно, или вручную через настройки питания). Если ПК всё-таки ушёл в suspend во время GPU-прогона — после wake мониторить лог: если flush stdout остановился >5 мин при 98% CPU и GPU util <10% — это busy-loop, перепрогон на CPU. Ждать смысла нет.
**Теги:** #cuda #cublas #suspend #busy-loop #transcribe #faster-whisper #performance #environment

### 2026-05-28 — pypdfium2 не поддерживает pdf[-1] в постпроверке generate_pdf ❌ провал
**Контекст:** генерация PDF для `nikita_muzh_klub` по процедуре из `.claude/skills/generate_pdf/SKILL.md`. Постпроверка вёрстки берёт последнюю страницу как `pdf[-1].get_textpage()...` (строка ~271 в SKILL.md).
**Симптом:** `pypdfium2._helpers.misc.PdfiumError: Failed to load page.` на `pdf[-1]`. Сам PDF при этом уже отрендерился корректно — падает только проверка last_orphan.
**Причина:** в установленной версии pypdfium2 (Python 3.14, `~/.local`) `PdfDocument.__getitem__` вызывает `get_page(i)` → `FPDF_LoadPage(i)`, который не принимает отрицательный индекс. Срабатывает на ЛЮБОМ запуске generate_pdf, не только на этом клиенте.
**Решение:** заменить `pdf[-1]` на `pdf[n_pages - 1]` (где `n_pages = len(pdf)`). `pdf[0]` работает нормально, проблема только в отрицательном индексе. **Правило на будущее:** для pypdfium2 индексировать страницы только неотрицательными числами: последняя = `pdf[len(pdf)-1]`.

### 2026-06-01 — Статический скриншот не видит scroll-reveal контент 💡 knowledge
**Контекст:** визуальная оценка лендингов через sales-evaluator. Снимал прод системным `chromium --headless --screenshot` (без скролла), отдавал PNG оценщику.
**Симптом:** на лендинге коуча (`kp-nikita-v1-fix`) бóльшая часть страницы вышла пустой — тёмные секции без контента. Наш лендинг снялся нормально (у нас `.reveal` только на hero), и это создало ложное впечатление, что наш «полнее» — сравнение было бы нечестным в нашу пользу.
**Причина:** контент появляется по scroll-reveal (IntersectionObserver / opacity:0 → .in на скролле). Статический скриншот не скроллит → элементы остаются невидимыми (opacity 0). Полностраничный chromium-скриншот тоже не триггерит reveal (fixed-noise рисуется только в первом вьюпорте, reveal-секции не «входят» во вьюпорт без реальной прокрутки).
**Решение:** снимать через `playwright-core` + системный chromium (`executablePath:/usr/bin/chromium`), ПРОКРУТИТЬ всю высоту страницы шагами с паузами (триггерит IntersectionObserver), вернуться вверх, подождать, затем `fullPage` screenshot. DPR=2 на полной высоте длинной страницы (>15k px) упирается в лимит текстуры — playwright ститчит fullPage сам, либо снимать DPR=1 нативно (резко) и нарезать `magick -crop` на тайлы.
**Правило на будущее:** для визуальной оценки/сравнения лендингов — ВСЕГДА скролл по всей высоте перед захватом (playwright/puppeteer), иначе scroll-reveal секции пустые и сравнение ложное. Статический `chromium --screenshot` годится только для страниц без scroll-анимаций.
